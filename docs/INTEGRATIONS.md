# Integration contracts and operating rules

## Billing
All persisted money is integer paise (INR). A started minute is rounded up; the final minor-unit amount is rounded up once. Sessions reserve the full prepaid amount. Ending a session consumes its capped actual charge and releases the unused hold. The starting hourly rate survives transfers and later rate changes. Pauses stop billing; resume extends expiry by the pause duration only if reservations permit it. Manual crashes should be paused by staff; automatic crash detection is not connected. Expired sessions close in the venue service, independently of the browser. An agent must enforce the same signed grant locally before unattended lockout is safe.

## Ownership and offline boundaries
Deploy the API with `Runtime__Mode=VenueController` inside the café using local PostgreSQL. It owns active sessions, reservations and ledger writes. A cloud instance rejects local session/booking commands. Existing session reservations cap billing during internet outages because the venue API and PostgreSQL remain local. A failed database or controller is not equivalent to an internet outage; install and validate the agent before relying on automatic access termination. The separate Controller project demonstrates durable SQLite grant expiry and an outbox. It is a simulator, not a fully integrated cloud synchronizer.

Production cloud booking requires PendingVenue -> authenticated venue acknowledgement -> Confirmed. Do not independently accept cloud bookings against a disconnected venue. Current booking endpoints confirm only on the venue controller. Deposits are fixed to zero; cancellations are free; no-show is a staff state transition. Nonzero deposits and configurable cancellation penalties remain production work.

## Device contract
Each Windows device requires a unique certificate, revoked-device handling, HTTPS/mTLS and monotonic sequence numbers. Grant fields: venueId, stationId, sessionId, issuedAt, expiresAt, reservedMinor, sequence, signature. Reject wrong-device, expired, replayed or invalid signatures. Never accept shell commands from a browser. Keep the privileged Windows Service separate from a restricted-user launcher. Official launchers retain their own authentication; no platform passwords are collected. Signed update packages need signature and rollback verification before execution. This repository's Agent only logs simulated heartbeats and performs no lockdown or updates. Console access remains manual.

## Razorpay
Server variables: Razorpay__KeyId, Razorpay__KeySecret, Razorpay__WebhookSecret; live mode also requires Razorpay__AllowLive=true. Use test credentials first. Configure payment.captured webhooks at `/api/payments/razorpay/webhook`. HMAC-SHA256 verifies original bytes with constant-time comparison. Checkout verification uses the database order ID. The server fetches the payment with merchant credentials and verifies capture, order, amount and INR before crediting. Both callback and webhook credit at most once under a row lock and unique references. Ambiguous order-creation timeouts remain pending for reconciliation; do not blindly create a second order. Real test transactions, disputes and provider refunds require configured credentials and further acceptance testing.

## n8n
Local editor: http://127.0.0.1:5678. Finish owner setup yourself. Import `automations/cafe-events.json`. Set its Header Auth credential to header `X-Dragon-Token`, using the same secret as server `N8n__HeaderSecret`. Activate the workflow, then set `N8n__WebhookUrl` to its production webhook URL. A persistent PostgreSQL outbox retries at-least-once delivery with exponential backoff and a ten-attempt cap. Receivers must deduplicate eventId before any external side effect. The included workflow validates and acknowledges events only; it does not send email, SMS, WhatsApp, or Slack messages. Add destinations explicitly after configuring credentials. Delivery success means webhook acknowledgement, not completion of downstream business actions.

## Deployment
Vercel hosts the React frontend. ASP.NET requires a separate container/VM host. Use a same-origin reverse proxy for `/api` and `/hubs`, HTTPS, persistent DataProtection keys and exact trusted origins. Vite supplies that proxy locally. `VITE_API_URL` is available for API origin configuration, but cross-origin cookies require additional tested CORS and cookie configuration; same-origin routing is the default. Do not expose the owner bootstrap endpoint on a public API before the owner is initialized or a one-time setup gate is added. Do not expose local PostgreSQL or n8n directly to the internet.
